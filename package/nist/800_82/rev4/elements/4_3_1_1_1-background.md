Network and computing devices (e.g., routers, gateways, switches, firewalls, servers, workstations) should be configured to log events to support monitoring, alerting, and incident response analysis. Logging capabilities are typically available for recording events in applications, OSs, and network communications. Logging should also be configured and collected from any external computing platforms used by the organization, such as cloud services.

Capturing log events is critical to maintaining situational awareness of the OT system. Organizations should review their available logging capabilities and configure them to record the operational and cybersecurity events that are appropriate for their environment. Typical events include maintenance functions (e.g., access control, configuration changes, backup, restore), OS functions, and application (i.e., process) events. The specific types of events available for logging will vary between OT devices and should be chosen based on the device’s capabilities and the desired events to capture. In general, each log entry should also include where the event occurred, the type of event, when it occurred, the source of the event, the identities of any users or system accounts involved, and the outcome of the event. To support log correlation, each log entry should identify the device that generated the event, the timestamp of the event, and the user or system account that generated the event. Correlating events across multiple OT devices can be difficult if the event timestamps generated by the devices were not informed by a shared time source. Each device’s internal clock should be synchronized with a primary clock to support event correlation across devices. Log entries should also use a consistent timestamp format (e.g., time zone format, string format, daylight saving). Organizations should verify timestamp consistency after log collection since device clock drift or loss of time synchronization can introduce discrepancies that affect the accuracy of event correlation and incident reconstruction.

Organizations should establish how long event logs should be retained and ensure that adequate storage is available to support log retention requirements. Many sector-specific regulations require data retention for a specific length of time. Depending on the frequency of events being logged, the log size may grow quickly and result in increasing space utilization. Disk space and memory are limited on most OT devices, so adequate storage should be provided locally or remotely to reduce the likelihood of exceeding device capacity, which could ultimately result in the loss of logging capability. Transferring logs from OT devices to alternate storage should be considered to free up device storage and ensure logs remain available for monitoring, analysis, and incident response.

Many OT devices either lack mechanisms to store logs or do not provide a network service that supports remote log collection (e.g., syslog). If device-level logs are unavailable, organizations should identify compensating data sources that can partially reconstruct activity on those devices. In this scenario, the engineering workstation or other programming terminal used to interact with the device is often the most valuable log source, as it may record engineering sessions, project file access, and maintenance activity even when the device itself cannot. Network infrastructure devices (e.g., switches, routers, firewalls) that sit adjacent to OT devices may also provide partial visibility through their own logs and capture connection activity and traffic patterns associated with those devices. Organizations should document which devices in their environment are incapable of generating or exporting logs and define compensating monitoring strategies for those device classes.

Organizations that use unidirectional gateways, data diodes, or similar devices to enforce highly segregated boundaries between OT and IT networks must explicitly design a security telemetry export path to ensure that security logs generated within the OT environment can still reach the IT SOC. These devices enforce one-way data flow by design, which can create a detection blind spot if this export path is not deliberately accounted for.
